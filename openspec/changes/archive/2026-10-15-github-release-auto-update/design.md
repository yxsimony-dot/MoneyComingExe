## Context

MoneyComing 当前使用 Electron 和 electron-builder，在 Windows 上只生成 `dir` 目录包，再由脚本压缩为 ZIP。应用的渲染窗口使用默认 Electron session，并通过 `webRequest.onBeforeRequest` 阻止全部 HTTP、HTTPS、WebSocket 请求；主进程没有版本更新服务，预加载层只暴露行情、规则说明和署名相关 IPC。

仓库已托管到 `yxsimony-dot/MoneyComingExe`。本次变更需要同时改动打包方式、主进程生命周期、预加载 IPC、渲染界面、测试和 GitHub Actions，因此采用独立的发布与更新架构。行为契约见 `specs/desktop-auto-update/spec.md` 和 `specs/github-release-publishing/spec.md`。

## Goals / Non-Goals

**Goals:**

- 建立 NSIS 安装版从 GitHub Releases 检查、下载并重启安装的完整链路。
- 让更新失败与现有离线行情查看能力解耦。
- 通过版本标签生成可重复、可验证、可匿名下载的正式 Release。
- 保持渲染进程无 Node.js 权限，并将更新操作限制在受信任 IPC。
- 为首次安装、后续升级和发布失败提供明确验证与回滚路径。

**Non-Goals:**

- 不支持 ZIP 便携版、自解压目录包或运行中覆盖应用目录。
- 不实现后台无提示强制更新、静默安装或远程强制最低版本。
- 不从 GitHub 普通分支 push、源码提交时间或文件哈希推断正式版本。
- 不在第一阶段建立独立更新服务器、差分补丁服务或私有仓库认证代理。
- 不把代码签名证书采购作为功能完成的硬前置条件，但保留后续签名配置入口。

## Decisions

### 1. 使用 electron-updater 与 electron-builder NSIS 目标

正式 Windows 产物使用 electron-builder 的 `nsis` target，运行时使用 `electron-updater` 的 GitHub provider 读取 Release 元数据、下载并调用 NSIS 更新安装。

选择该方案是因为它与现有 electron-builder 配置兼容，可生成标准更新元数据和校验信息，并处理 Windows 应用退出后替换文件的生命周期。自研下载器需要自行解决进程锁、权限、完整性验证、回滚和安装器启动，风险明显更高；目录包和 ZIP 也不具备可靠的原地自更新能力。

### 2. 保留渲染层断网策略，但将其与更新网络隔离

为 MoneyComing 窗口分配专用 Electron session，并仅在该 session 上阻止渲染层外部网络请求。更新器在主进程使用不受该渲染策略影响的网络通道访问 GitHub Releases。

这样可以继续保证行情界面无法任意访问互联网，同时允许受控的主进程更新请求。不得简单删除现有网络阻断，也不得向渲染层暴露通用 URL 下载接口。

### 3. 主进程维护单一更新状态机

主进程新增更新协调模块，持有以下有限状态：

```text
disabled --> idle --> checking
                    |       |
                    |       +--> up-to-date
                    |       +--> available
                    |       +--> failed
                    |
available --> downloading --> downloaded
                   |              |
                   +--> failed    +--> installing
```

启动检查和手动检查共用同一个进行中任务，避免重复请求。`autoDownload` 和退出时自动安装均关闭；只有用户确认后下载，只有用户确认“重启安装”后调用安装流程。更新错误转换为可展示状态，不向上抛出导致应用退出的未处理异常。

### 4. 通过白名单 IPC 暴露更新能力

预加载层只暴露以下语义化操作：

- 获取当前版本和当前更新状态。
- 请求检查更新。
- 请求下载已发现的版本。
- 请求重启并安装已下载版本。
- 订阅主进程发布的更新状态变化。

每个调用沿用现有 `trusted` 来源校验。事件载荷只包含版本、阶段、进度、可公开的发布说明摘要和用户可理解的错误，不包含本地下载路径、任意 URL、请求头或凭据。

### 5. 更新界面嵌入现有工具栏工作流

工具栏增加版本/更新入口，并使用小型状态区域或模态层呈现检查结果、版本信息、下载进度和重启安装动作。启动自动检查在窗口可用后异步执行；没有更新时不主动打扰用户，手动检查才明确显示“已是最新版本”。

发现更新时不遮挡行情加载。下载失败允许重试或关闭提示，下载完成后允许继续看盘并稍后通过同一入口重启安装。

### 6. 正式发布由语义化版本标签驱动

GitHub Actions 工作流监听 `v*` 标签，在 Windows runner 上执行以下阶段：

```text
检出标签
  --> 校验 tag == package.json version
  --> npm ci
  --> 类型检查与测试
  --> 构建 NSIS 安装包
  --> 安装包/更新元数据验收
  --> 创建 GitHub Release 并上传全部更新资源
```

普通 `main` push 可以运行持续集成，但不创建正式 Release。发布工作流显式配置 GitHub owner/repo，使用工作流运行期 `GITHUB_TOKEN` 和最小 `contents: write` 权限；客户端只匿名读取公开 Release。

Release 应在产物全部准备好后一次性公开，避免客户端短暂读到缺少安装包或元数据的版本。相同标签和版本不可覆盖，修复必须递增版本号并创建新标签。

### 7. 版本号是发布契约的一部分

`package.json` 版本是应用显示和比较的版本来源，Git 标签使用 `v<package-version>`。发布工作流在构建前校验二者一致。

首个具备更新能力的版本由现有 ZIP 用户手动下载 NSIS 安装包完成迁移。验证自动更新能力时必须再发布一个更高测试版本，从已安装的前一版本执行真实检查、下载和重启安装，不能只验证最新版本的全新安装。

### 8. 完整性与代码签名分层处理

第一阶段依赖 HTTPS、GitHub Release 访问控制以及更新元数据中的哈希校验拒绝损坏或被替换的下载文件。发布产物和客户端中不得包含写权限凭据。

Windows 代码签名作为强化项保留：若提供证书，CI 在发布阶段签名安装包和可执行文件；若暂未提供证书，发布说明和安装文档必须说明 Windows SmartScreen 可能出现未知发布者提示。无签名不会降低版本一致性、哈希校验和匿名访问验收要求。

## Risks / Trade-offs

- [仓库或 Release 不是公开可读] -> 在首次发布前使用未登录环境验证更新元数据和安装包 URL，失败则阻止发布。
- [当前 session 网络阻断误伤更新器] -> 将渲染窗口迁移到专用 session，并增加打包应用的真实更新网络验收。
- [无代码签名触发 SmartScreen] -> 清晰展示发布来源与校验信息，并预留 CI 签名配置；获得证书后启用正式签名。
- [错误标签向全部用户发布问题版本] -> 标签发布前执行完整质量门禁，禁止覆盖相同版本，并保留 GitHub Release 撤下作为紧急止损手段。
- [Release 上传到一半被客户端发现] -> 先生成并验证全部产物，再公开 Release；失败的草稿或未完整版本不得作为稳定更新源。
- [首次更新无法覆盖旧 ZIP 用户] -> 发布独立迁移说明，要求旧用户手动安装首个 NSIS 版本，后续版本再验证自动更新。
- [更新下载占用带宽或打扰看盘] -> 禁止自动下载，只在用户确认后开始，并允许失败后继续使用当前版本。

## Migration Plan

1. 在开发分支完成 NSIS 构建、更新状态机、界面、IPC 和自动化测试，不影响当前用户已有 ZIP 文件。
2. 确认 GitHub 仓库与 Release 资源可匿名访问，并在 GitHub Actions 中启用最小发布权限。
3. 递增应用版本，创建首个带更新能力的 NSIS Release；旧 ZIP 用户手动下载安装该版本。
4. 安装首个 NSIS 版本后，发布一个更高版本执行端到端升级验收，覆盖发现、下载、重启和版本变更。
5. 验收通过后，将文档中的正式下载方式改为 NSIS 安装包，并停止生成和上传 ZIP。
6. 若新发布失败，保留最后一个成功 Release 为最新稳定版本；若已公开版本存在严重问题，撤下该 Release 并发布更高修复版本，不覆盖旧标签。
