## Context

MoneyComing 当前在开发模式下从 `futures_investigation_20261009` 读取数据，在打包模式下从 EXE 同级 `data` 目录读取 `edb_main_continuous_5m.csv` 和 `edb_main_continuous_60m.csv`。数据服务只读并缓存静态 CSV；渲染页面通过受信任 IPC 加载数据，默认 Electron session 阻断全部外部 HTTP、HTTPS 和 WebSocket 请求。

现有 `collect.py` 是一次性全量采集脚本，固定请求从 2025-10-09 开始的一分钟数据。EDB 免费接口只允许有限历史范围，随着时间推移直接重跑会返回 HTTP 403，因此运行时必须从本地末尾执行增量请求。应用还存在 `github-release-auto-update` 变更，其设计同样要求渲染层断网、主进程受控联网和 NSIS 安装版；两项能力需要共享安全边界，但保持独立状态和 IPC。

行为契约见 `specs/incremental-market-data-update/spec.md`。

## Goals / Non-Goals

**Goals:**

- 从静态基线安全演进为可重复更新的用户行情快照。
- 复用现有北京时间交易分钟与 5 分钟、60 分钟聚合语义。
- 将联网、候选构建和有效快照切换隔离，任何中途失败都不损坏当前数据。
- 保持渲染层无 Node.js 权限和无任意外网访问能力。
- 让数据源延迟、数据截止时间和失败原因对用户可理解。

**Non-Goals:**

- 不提供实时行情推送、自动定时刷新或后台常驻采集。
- 不接入新浪等备用数据源，也不跨数据源补洞或比较后自动选值。
- 不在每次点击时重新下载全部历史，也不修订增量重叠区间之前的旧数据。
- 不把安装目录作为运行时可写数据目录。
- 不在本次更新中重新生成跨数据源审计结论。

## Decisions

### 1. 主进程使用固定 EDB 客户端，渲染 session 继续断网

主进程新增行情更新协调模块，只能构造以下固定请求：

```text
origin: https://edb.shinnytech.com
path:   /md/kline
symbol: KQ.m@DCE.m
period: 60
cols:   open,high,low,close,volume,open_oi,close_oi
```

请求通过未绑定任何渲染页面的专用 Electron session 发出，并设置超时、响应体上限和允许的内容格式。渲染窗口迁移到专用 viewer session 后继续阻断外部网络；该网络隔离方式与 `github-release-auto-update` 的设计协调，避免继续在 `defaultSession` 上采用会误伤所有主进程请求的全局拦截。

preload 只暴露获取更新状态、触发更新和订阅状态变化的语义化 API，不接受 URL、symbol、文件路径或请求头。所有 IPC 沿用主窗口、主 frame 和 `app://viewer/` 来源校验。

选择主进程固定客户端，是因为它既能满足联网需求，又不会扩大渲染层攻击面。直接放开 CSP 或 renderer fetch 会破坏当前离线安全边界；调用外部 Python 则会给打包、运行时依赖和进程管理增加不必要复杂度。

### 2. 使用单一更新状态机并合并并发请求

主进程维护以下状态：

```text
idle --> fetching --> validating --> saving --> succeeded
  |         |             |           |
  |         +-------------+-----------+--> failed
  |
  +----------------------------------------> up-to-date
```

同一时间最多存在一个更新 Promise。重复点击复用当前状态而不创建第二条下载链路。状态载荷包含阶段、当前快照最新时间、数据源最新分钟结束时间、两个周期新增或替换数量、开始/完成时间和可公开错误；不包含本地绝对路径、响应正文或内部堆栈。

### 3. 从完整自然日边界回退并分块请求

更新服务读取当前有效 5 分钟和 60 分钟快照，以两者最晚记录所在的北京时间自然日为锚点，将请求起点回退到前一个自然日 `00:00:00`，请求终点取当前北京时间。跨度较长时按固定天数分块，逐块请求后以 `datetime_nano` 合并、排序和去重。

完整自然日回退能够覆盖最后一个日盘、夜盘和两个聚合周期的尾部，避免只从最后一根结束时间请求导致 60 分钟桶缺少组成分钟。分块请求可以限制单次响应体和内存占用，也便于明确报告某一段失败。若本地数据早于 EDB 可访问边界，整次更新失败并保留旧快照，不提交部分结果。

替代方案是保存并持续追加全部一分钟原始数据，但现有发布基线没有包含完整原始文件，迁移成本和磁盘占用更高；当前需求只需要可靠生成两个展示周期，因此不把原始响应作为有效快照的一部分。

### 4. 以分钟覆盖结束时间决定可提交的聚合桶

下载的一分钟记录先经过字段、时间、数值和交易时段校验，再使用现有交易分钟时钟聚合。候选结果只保留 `bar_end` 不晚于“最新有效一分钟开始时间加一分钟”的时间桶：

- 已经结束但缺少组成分钟的桶可以保留，并标记 `complete=false`。
- 尚未到理论结束时间的当前 5 分钟或 60 分钟桶不写入快照。
- 日盘最后一个 60 分钟桶继续使用 14:15-15:00 的 45 交易分钟定义。

该规则避免盘中更新时产生结束时间位于未来的 60 分钟 K 线，同时保留现有对真实历史缺口的可见表达。

### 5. 按切换点重建尾部，而不是逐字段拼补

请求起点同时作为聚合切换点。新快照由“本地 `bar_start` 早于切换点的记录”与“本次一分钟数据重新聚合的记录”组成。这样可以自然吸收 EDB 对重叠尾部的修订，并删除重叠区间中不再存在的旧记录。

提交前对候选执行完整校验：

- 必需列齐全，时间戳严格递增且唯一，时间属于允许的日盘或夜盘分钟。
- OHLC、成交量和持仓量为有限合法值。
- 5 分钟和 60 分钟记录严格有序、区间不重叠、完整性字段自洽。
- 每根 60 分钟 K 线与其包含的 5 分钟 K 线核对开、高、低、收和成交量。
- 候选最晚有效时间不得早于当前快照，且远端区间必须与本地尾部存在可验证重叠。

逐行追加虽然实现更短，但无法安全处理源端修订、重复边界和半根聚合桶，因此不采用。

### 6. AppData 使用不可变快照和原子指针

运行时目录使用 `app.getPath('userData')/market-data`，结构如下：

```text
market-data/
  current.json
  snapshots/
    <snapshot-id>/
      edb_main_continuous_5m.csv
      edb_main_continuous_60m.csv
      metadata.json
```

`metadata.json` 记录 schema 版本、固定数据源、生成时间、请求覆盖范围、最新有效分钟结束时间、行数和文件哈希。保存流程先在新的 snapshot 目录写入全部文件，再从磁盘重新读取并使用正式解析器校验；成功后写入临时指针并原子替换 `current.json`。切换后保留至少一个上一版本快照，再清理更旧且未被引用的快照。

启动加载顺序为：

```text
有效 current.json 用户快照
  --> 若无效，回退上一完整用户快照
  --> 若仍不可用，读取安装包内置基线
```

安装包数据保持只读，NSIS 升级不得覆盖 AppData。该方案比同时覆盖两份 CSV 更可靠，因为任何时刻 `current.json` 都只指向一个已经完整验证的目录。

### 7. 数据服务拆分价格快照与静态辅助资料

价格 CSV 从当前有效用户快照或内置基线读取；`entry-rules.md` 和可选的 `cross_source_audit.json` 继续从内置数据目录读取。用户快照只承担 EDB 价格更新，不复制规则文件，也不把旧审计资料伪装成对新增区间的审计。

`Dataset` 增加快照来源、数据源最新时间和更新时间元数据。现有缓存仍保留，但快照切换成功后必须失效并从新目录重新加载。

### 8. 更新界面复用现有工具栏和加载流程

工具栏新增带刷新图标的“更新行情”按钮。更新中按钮禁用并显示阶段；结束后通过现有 toast 或紧凑状态区域显示：

- `已更新：5 分钟 +N，60 分钟 +M，数据源最新至 ...`
- `已是数据源当前最新：...`
- `更新失败：...，当前数据未受影响`

图表重载前记录当前模式、开关、选中时间和可见区间中心；重载后优先恢复原时间位置。更新动作本身不调用现有“最新”逻辑，用户仍可用“最新”按钮跳到新增末尾。数据覆盖信息明确区分“本地快照更新于”和“数据源最新至”，避免将历史更新误解为实时连接。

## Risks / Trade-offs

- [EDB 接口、字段或访问限制变化] -> 固定请求契约并严格校验；失败时保留旧快照，错误信息提示稍后重试而不猜测或切换数据源。
- [长时间未更新导致起点超出免费历史边界] -> 分块请求并在首个不可访问区间停止；不提交不完整缺口，后续通过新版内置基线或人工数据迁移恢复。
- [源端修订发生在重叠窗口之前] -> 本次只保证尾部重叠区间可修订；不进行受一年限制影响的全历史重抓。
- [盘中更新产生半根周期数据] -> 仅提交理论结束时间不晚于最新分钟覆盖结束时间的桶。
- [磁盘写满、杀进程或安全软件占用文件] -> 使用不可变候选目录和原子指针，切换失败继续引用旧快照，并在后续启动清理未引用临时目录。
- [用户快照 schema 与未来版本不兼容] -> 在 metadata 中记录 schema；新版本先迁移或回退内置基线，不直接按未知结构加载。
- [应用更新与行情更新同时占用网络或状态区域] -> 两者使用独立协调器和状态，工具栏分别展示；不得共享任意 URL IPC 或互相覆盖错误。

## Migration Plan

1. 在不改变现有内置 CSV 的前提下，引入快照解析、聚合、校验和 AppData 存储模块，并用临时目录测试原子切换与回退。
2. 将数据服务改为优先加载用户快照、回退内置基线；无用户快照时行为与当前版本保持一致。
3. 增加固定 EDB 网络客户端、主进程更新状态机、受信任 IPC 和 preload 类型。
4. 增加工具栏按钮和状态反馈，完成更新后缓存失效与图表上下文恢复。
5. 使用受控 EDB 响应夹具验证缺口补齐、无新数据、源端修订、盘中半桶、HTTP 失败、非法数据和保存中断。
6. 在开发版和 NSIS 安装版执行真实增量更新验收，确认数据写入 AppData、重启后继续生效、升级后不被内置基线覆盖。
7. 若上线后发现问题，可禁用更新入口并继续读取最后一个有效用户快照；必要时删除无效指针即可回退内置基线，不需要修改安装目录。
