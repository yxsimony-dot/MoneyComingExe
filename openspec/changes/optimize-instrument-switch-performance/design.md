## Context

参见 `proposal.md` 的变更动机和 `specs/instrument-switch-performance/spec.md` 的行为合同。当前真实五年基线中，单个品种约有 8.28 万根 5 分钟 K 线和 8,400 根 60 分钟 K 线。打包 EXE 离屏测量显示：

- 直接执行一次未缓存 IPC 加载约为 `4355.5 ms`；
- 先声明当前品种再加载约为 `8499.9 ms`，而声明调用本身只耗时约 `0.6 ms`；
- 完整界面冷切换中位数约为 `8487 ms`，缓存切换中位数仍约为 `3872 ms`；
- 顺序访问多个品种后 Electron 进程树工作集可接近 `2887 MiB`。

测量时在线模式处于关闭状态。当前声明路径仍会在后台调用完整 `loadSnapshot()`，随后界面 `load()` 再次读取和解析相同快照；数据服务的完成缓存是无容量上限的 `Map`。渲染层在一次提交中还会重复生成周期数据、策略生命周期和盈亏结果，并可能对同一 K 线序列多次执行 `setData()`。

```text
当前冷切换

选择品种
   |
   +--> setCurrentInstrument()
   |        |
   |        +--> loadSnapshot() --> 读取 + CSV 解析 + 校验
   |
   +--> market.load()
            |
            +--> loadEffectiveSnapshot() --> 再次读取 + CSV 解析 + 校验
                                            |
                                            +--> 图表 + 策略 + 复盘重复计算
```

实现还必须遵守项目的离屏 GUI 测试规则：Electron JavaScript 测试统一通过 `tests/electron-test-launch.mjs` 启动，直接 EXE、安装版和快捷方式使用 `--test-window-offscreen` 并验证窗口矩形与全部显示器无面积交集。

## Goals / Non-Goals

**Goals:**

- 让同一品种和快照的所有并发消费者共享一次数据准备，并消除在线模式关闭时的隐藏快照解析。
- 使用容量为三个完整 Dataset 的 LRU，将内存从“随访问品种数增长”改为可验证的固定边界。
- 让快速连续切换保持立即响应，并只允许最后一个请求提交界面与在线状态。
- 复用图表、策略和复盘所需的派生结果，减少全历史重复遍历和重复图表写入。
- 把 CSV 解析、校验和时间索引构建移出主线程关键路径，为后续更大 1 分钟数据保留扩展空间。
- 用真实五年基线、生产构建和统一离屏环境固定性能回归门槛。

**Non-Goals:**

- 不缩短五年行情，不减少十五个品种，不删除 1 分钟后台证据。
- 不改变主力换月、入场、止盈、止损、休市出场、复盘资金或日期范围规则。
- 不在本变更中改用数据库、改变 CSV 发布格式或重新设计行情快照 schema。
- 不预加载全部十五个品种，不让在线模式自动轮询非当前品种。
- 不以降低图表数据精度、抽样 K 线或隐藏策略结果换取性能。

## Decisions

### 1. 在数据服务内部建立共享的数据准备单航班

数据服务增加按品种管理的在途表。内部统一的数据准备结果同时包含构造 Dataset 所需的快照数据和在线协调器所需的快照摘要；`load()` 与 `loadSnapshot()` 不再分别进入两条完整解析路径。

```text
load(instrument) --------+
                         |
loadSnapshot(instrument) +--> prepareInstrument(instrument)
                                  |
                                  +--> 命中 Dataset/摘要缓存
                                  |
                                  +--> 命中 in-flight Promise
                                  |
                                  +--> 唯一一次读取、解析、校验和索引
```

在途键首版使用品种标识，因为每个品种只有一个当前有效快照；行情更新激活新快照时先调用该品种的失效操作，再触发重新加载。显式 `reload` 也先失效完成缓存，然后复用或创建一个新的在途任务。任务只在全部校验成功后进入完成缓存，并在 `finally` 中从在途表删除，失败结果不会污染后续重试。

备选方案是在 IPC 或渲染层合并两个 Promise。它无法阻止主进程内其他消费者再次解析，也会把快照一致性责任分散到多个调用方，因此不采用。

### 2. 在线模式关闭时声明品种不读取行情

`declareCurrentInstrument()` 始终同步更新协调器的品种、世代号和状态，但在线模式关闭时不启动快照准备或补齐门禁。在线模式开启时才请求快照摘要，并通过决定 1 的单航班与界面加载共享数据准备。

在线任务继续携带世代号；任何返回结果在提交前都检查世代号、目标品种和当前阶段。这样即使旧任务已经进入 Worker 或文件读取，迟到结果也只能用于受限缓存，不能恢复旧品种的在线状态。

备选方案是让声明接口等待界面 Dataset 完成后再由渲染层回传摘要。该方案增加新的双向 IPC 时序和信任边界，现阶段复用主进程数据准备更直接。

### 3. 完成缓存使用容量为三的 LRU

完成缓存保存最近使用的三个完整 Dataset。读取命中时通过删除后重新插入刷新顺序；成功加入第四个品种后驱逐最久未使用项。容量三覆盖“当前品种、刚离开的品种、另一个常用对比品种”，同时避免十五个五年 Dataset 常驻。

与 Dataset 强绑定的时间索引和派生分析使用同一缓存条目或 `WeakMap` 保存，不能由独立全局 `Map` 延长被驱逐 Dataset 的生命周期。渲染进程只保留当前已提交 Dataset 和当前切换必要的短期引用。失效操作只删除指定品种；全局清空仅用于明确的测试或进程退出场景。

备选方案：

- 容量二内存更低，但用户在三个常用品种之间切换时会持续抖动；
- 按字节动态估算更精确，但 JavaScript 对象实际驻留大小难以稳定测量，首版以固定条目数和进程工作集双重验收更可控；
- 缓存十五个品种可提高再次切换速度，但已实测导致约 2.9 GiB 工作集，不采用。

### 4. 渲染层使用请求世代和显式切换状态

每次选择品种立即递增切换世代、记录 `requestedInstrument` 并显示加载状态。异步阶段可以继续执行，但提交函数必须同时满足：

- 返回世代等于当前世代；
- 返回品种等于 `requestedInstrument`；
- Dataset 已通过完整校验。

成功提交后才更新 `currentInstrument` 和选择器的已加载标识。失败时恢复选择器到最后成功品种，保留最后成功的完整界面并显示目标品种错误。切换期间再次选择新目标只需创建新世代，不等待旧 Promise。

不强制取消已经开始的文件读取或 Worker 任务，因为 Node 文件读取和 CPU 任务的中途取消收益有限且容易留下半成品状态；旧任务完成后可以按 LRU 规则进入缓存，但不能提交界面。

### 5. Worker 负责纯数据准备，主进程负责快照选择和缓存

主进程先完成有效快照目录选择和文件存在性判断，然后把不可变的文件路径、品种定义和校验参数交给 Node Worker。Worker 执行：

1. 读取 1/5/60 分钟、主力映射、换月和可选审计文件；
2. CSV 解析、字段规范化和完整性校验；
3. 构造按时间有序的 Dataset 数据；
4. 构造可序列化的时间索引元数据和加载诊断。

主进程接收成功结果后构造最终 Dataset、写入 LRU 并通过 IPC 返回。Worker 不选择用户快照、不修改当前指针、不写入行情文件，也不拥有缓存淘汰权。测试保留同步参考入口，以固定夹具逐项对账 Worker 结果。

Worker 首版仍返回现有对象结构，避免同时引入二进制行情格式迁移。若对象结构化克隆仍是冷切换主要瓶颈，后续可以在不改变规格的前提下把 K 线列转换为可转移 `ArrayBuffer` 或生成预编译快照；该后续目标是把冷切换进一步压到约 `1–2 s`，但本变更的硬验收线为 `4.5 s`。

备选方案是在渲染进程使用 Web Worker 解析。它需要把大体积原始文本先通过 IPC 送入渲染侧，增加复制和安全面，因此不采用。

### 6. 为分钟记录和 K 线建立可复用时间索引

每个 Dataset 派生一个只读时间索引，至少包含：

- 1、5、60 分钟记录的有序开始时间数组；
- 开始时间到记录位置的精确索引；
- 用于区间查找的二分下界和上界操作。

`completeMinutesForFiveMinuteBar()` 等热点路径不再对全部 1 分钟记录执行 `filter()`；生命周期计算通过索引取得目标 5 分钟区间的候选分钟。索引随 Dataset 生命周期缓存，快照失效或 LRU 驱逐时一起释放。

备选方案是为每根 5 分钟 K 线复制对应分钟数组。它会显著增加长期 1 分钟数据的常驻对象数量，因此使用共享记录加索引范围。

### 7. 建立一次性的派生分析并在图表与复盘间复用

Dataset 提交前后分两层派生结果：

- **行情派生层**：图表点、EMA、周区间、入场候选、时间索引和换月定位，只依赖 Dataset；
- **策略派生层**：完整入场生命周期和资金计算，键由 Dataset 身份及会影响规则结果的策略设置组成。

日期范围只对已生成生命周期做筛选，不重新扫描完整 1/5 分钟历史。图表标记、设置面板盈利摘要和盈亏复盘都消费同一策略派生结果。策略设置变化时只失效策略派生层，不失效 Dataset 或行情派生层。

盈亏弹窗关闭时不构造逐笔交易 DOM 和仅供弹窗展示的格式化字段；打开弹窗时基于当前策略派生结果生成。若切换或设置变化发生在弹窗打开期间，仍以当前世代和当前设置重新提交。

备选方案是分别优化 `refreshEntryStrategy()` 和 `reviewProfitLoss()` 内部循环。它仍会维护两套全历史计算和结果对应关系，难以证明图表与复盘使用同一生命周期，因此不采用。

### 8. 图表切换采用计算与提交分离的单次事务

图表实例继续复用，但切换分为“准备视图模型”和“提交视图”两步。准备阶段计算 candle、EMA、成交量、持仓量、标记和诊断数组；提交阶段每个可见周期只对每个系列调用一次必要的 `setData()`，之后恢复模式、视口和选择状态。

切换事务中，`setInstrumentDefinition()`、副图可见性和策略标记更新不得隐式用旧 `bars` 触发一次提交，再由 `setData()` 触发第二次提交。普通用户之后切换周一标记或副图时仍可独立刷新对应系列。

为了让加载状态先绘制，开始重计算前至少让出一次渲染机会。较重的渲染侧数组转换按可中断的小批次执行，或移动到 Worker 生成可直接提交的视图模型，保证没有超过 50 毫秒的渲染长任务。

### 9. 性能诊断使用稳定事件和真实生产数据

增加只在测试模式暴露的诊断计数：

- 每品种数据准备开始、完成、失败和缓存命中次数；
- 当前在途数、完成缓存大小和 LRU 顺序；
- 切换请求、加载状态、Dataset 就绪、图表提交、策略摘要可用时间；
- 每个周期和系列的完整 `setData()` 次数；
- 策略派生和盈亏明细生成次数。

性能脚本使用生产构建与真实五年基线，在线模式关闭，窗口尺寸固定为 `1440 x 900`，并通过统一离屏启动器启动。脚本至少覆盖：

1. 未缓存品种切换三次并取中位数；
2. 缓存内品种往返三次并取中位数；
3. 快速 A -> B 切换验证最后请求获胜；
4. 顺序访问十五个品种并采样 Electron 全进程工作集；
5. 使用 Long Tasks API 记录渲染长任务；
6. 核对逻辑数据准备次数、缓存上限和图表提交次数。

原始结果写入 `artifacts/`，阈值失败必须使命令返回非零。测试不得改变普通用户启动位置或启动参数。

## Risks / Trade-offs

- [三条 Dataset 缓存仍可能超过不同机器的理想内存] -> 同时以条目数和 `1.5 GiB` 进程树工作集验收；若真实对象大小超预算，先压缩派生对象或减少重复引用，再考虑把默认容量降为二。
- [Worker 返回大量对象时结构化克隆仍耗时] -> 先测量读取、解析、Worker 克隆、IPC 克隆和渲染各阶段；必要时引入可转移列式缓冲或预编译快照，不降低数据完整性。
- [单航班与显式 reload 竞态导致旧结果重新入缓存] -> 每个品种维护失效世代；任务完成时只有世代仍匹配才能写入完成缓存。
- [旧请求虽不提交界面但仍占 CPU 和内存] -> 在途任务按品种唯一，完成后受 LRU 约束；后续仅在测量证明必要时增加 Worker 取消协议。
- [派生缓存键遗漏策略参数产生陈旧结果] -> 集中生成规范化设置键，并用逐参数变更测试验证对应层失效和结果对账。
- [分批渲染改变图表可用时点或视口恢复顺序] -> 只有两周期数据和策略摘要均提交后才标记切换完成，视口与选中状态在最终提交事务中恢复。
- [性能阈值受后台负载影响] -> 使用同机生产构建、三次中位数和原始阶段数据；功能 CI 与参考机性能门禁分开报告，但发布前两者都必须通过。

## Migration Plan

1. 先增加诊断计数和真实五年切换基准，固定当前慢路径、内存和结果哈希。
2. 引入数据准备单航班，并让在线模式关闭时的声明路径不读取快照；以单元和 IPC 集成测试证明一次切换只有一次逻辑准备。
3. 将完成缓存替换为容量三的 LRU，并让 Dataset 相关索引和派生缓存跟随淘汰与失效。
4. 增加时间索引和 Worker 数据准备，对固定夹具与真实基线执行同步参考路径对账。
5. 在渲染层接入请求世代、立即加载状态、派生结果复用、单次图表事务和延迟盈亏明细。
6. 运行类型检查、完整测试、真实基线、离屏 Electron、打包 EXE、安装版和快捷方式性能验收，再记录冷切换、缓存切换、长任务和内存结果。

每一步都保持现有 CSV、快照和 Dataset 外部语义。若 Worker 或渲染事务在发布前出现回归，可以回退到前一阶段实现而不迁移用户数据；但最终发布必须满足规格中的性能与一致性阈值。
