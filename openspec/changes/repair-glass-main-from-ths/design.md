## Context

参见 `proposal.md` 的动机。本工程当前使用 schema v5 保存完整快照、使用 schema v6 保存有界尾部层；快照已经具备来源分段、文件哈希、候选校验、原子指针切换、前一有效快照回退和按品种隔离。在线更新由 `MarketUpdateCoordinator` 合并 EDB 1 分钟尾部并重建 5/60 分钟，由 `OnlineMarketCoordinator` 在完整补齐门禁通过后按北京时间分钟边界轮询。

当前 `glass_main` 有效快照与同花顺 `FG9999` 在 `2021-10-18 09:05` 至 `2026-10-22 15:00` 间均有 83,088 根 5 分钟记录，时间戳没有缺失或多余，但 OHLC 一致率约为 84.863%，OHLCV 一致率约为 77.129%，最大价格偏差为 292 点。差异主要集中在主力换月选择不同的连续区间，例如 `2023-08-09 09:05` 本地映射为 `FG2401`，同花顺主连仍对应 `FG2309`。

现有 schema 没有“外部基准保护字段”的语义，现有 `MarketSnapshotSourceKind` 也无法明确表示同花顺基准段。当前 v5 校验要求 1 分钟与 5 分钟覆盖一致，而基准修复后保留的 EDB 1 分钟可能无法聚合出同花顺 5 分钟 OHLCV，因此需要把“后台分钟证据”和“受保护可见周期”分开校验。未确认同花顺数据再分发授权，所有原始数据和修复结果只能保留在用户 AppData。

## Goals / Non-Goals

**Goals:**

- 提供固定面向 `glass_main` 的本地维护流程，可重复拉取、规范化、比较和激活同花顺 `FG9999` 5 分钟基准。
- 明确 5 分钟 OHLCV、持仓量、后台 1 分钟、60 分钟、主力映射和换月记录各自的权威来源。
- 让后续 EDB 完整补齐和分钟轮询只能接续基准边界之后的尾部。
- 保持现有离线复盘、双周期交互、快照回退和在线模式状态机不变。

**Non-Goals:**

- 不在本变更中修复其他十四个品种，也不抽象面向任意行情网站的通用下载器。
- 不增加渲染层同花顺网络访问、可见 1 分钟图表或新的用户操作入口。
- 不把同花顺数据写入仓库内置基线、EXE 或安装包。
- 不根据价格跳变、最大持仓量或人工日期表直接猜测受保护区间的换月。

## Decisions

### 1. 使用独立的本地维护 CLI，而不是把同花顺接入日常在线轮询

新增只允许 `glass_main` 的维护 CLI。CLI 在主进程/Node 信任边界内运行，直接复用行情领域模型和快照保存能力，不通过 preload 或渲染进程暴露网络参数。同花顺只负责一次性历史基准修复；日常每分钟收盘更新仍使用现有 EDB 客户端。

每次运行使用独立目录：

```text
%APPDATA%/MoneyComing/market-data/repairs/glass_main/<run-id>/
  request.json
  raw/pages/*.json
  normalized/ths_fg9999_5m.csv
  reports/field-diff.json
  reports/minute-reconciliation.json
  reports/contract-matching.json
  reports/activation.json
```

原始分页响应先落盘并计算 SHA-256，再进入规范化。失败运行不删除，便于复核；只有最终候选进入品种快照目录。CLI 提供默认的只比较模式和显式 `--activate` 模式，激活前再次读取报告与原始哈希，避免“比较时的数据”和“写入时的数据”不一致。

同花顺主连请求固定为：

```text
POST https://quota-h.10jqka.com.cn/fuyao/common_hq_aggr/quote/v1/single_kline
```

```json
{
  "code_list": [{ "codes": ["FG9999"], "market": "67" }],
  "trade_class": "intraday",
  "time_period": "min_5",
  "trade_date": -1,
  "begin_time": -999,
  "end_time": 0,
  "adjust_type": "forward",
  "gpid": 1
}
```

第一页使用 `end_time: 0`，后续页使用上一页最早时间戳减 1 毫秒。每页最多接受 999 根，空页或不再前移时结束。字段 `1/7/8/9/11/13/19` 分别作为收盘时间、开、高、低、收、成交量和成交额；成交额仅进入审计，不作为本次快照替换字段。

**替代方案：** 把同花顺作为第二个在线数据源。该方案会增加凭据、限流、延迟状态和跨源切换复杂度，也超出用户当前“先修复本地历史、继续使用现有在线模式”的范围，因此不采用。

### 2. 先规范时间，再按时间戳做集合比较

适配器将同花顺时间戳解释为 K 线收盘边界：

```text
barEndMs = thsTimestampMs
barStartMs = barEndMs - 5 * 60_000
```

随后调用玻璃交易时段工具确认该区间是唯一合法 5 分钟桶，并补全 `start`、`end`、`session`、`observedMinutes`、`expectedMinutes` 和 `complete`。记录按 `barStartMs` 排序，重复、倒序、非法时段或非闭合记录立即使运行失败。

比较器以 `barStartMs` 为键计算双方集合。选定保护区间内必须一一对应，不允许按数组下标对齐。报告同时输出：

- 双方行数、首末时间、缺失与多余时间戳；
- O/H/L/C/V 各字段一致数、一致率、差异数和绝对差；
- 最大价格偏差及其时间戳；
- 连续差异区间，辅助识别换月影响。

当前 83,088 根对比结果作为真实数据验收基线写入运行报告，但不硬编码进业务逻辑；未来运行以实际闭合数据和选定保护范围为准。

**替代方案：** 直接按同花顺返回顺序覆盖本地 CSV。该方案无法发现中间缺失、重复和时区偏移，故不采用。

### 3. 使用按字段划分的权威矩阵合并候选

修复候选按以下权威矩阵生成：

| 数据 | 基准保护区间 | 保护边界之后 |
| --- | --- | --- |
| 5 分钟 O/H/L/C/Volume | 同花顺 `FG9999` | EDB 1 分钟聚合 |
| 5 分钟 OpenOI/CloseOI | 当前最后有效本地快照 | EDB 1 分钟聚合 |
| 60 分钟 | 最终 5 分钟完整重建 | 最终 5 分钟完整重建 |
| 1 分钟 | 保留当前本地记录，仅作后台证据 | EDB 新尾部 |
| 主力映射与换月 | 基准匹配证明 | EDB 后续映射 |

同一 5 分钟时间戳的 OHLCV 来自同花顺，持仓量及其余非基准属性逐值复制自当前有效快照。任何无法唯一对应或缺少有效持仓字段的记录都阻止激活。60 分钟不做局部拼补，而是从最终完整 5 分钟数组重新聚合，以消除修复前的派生残留。

1 分钟数据原样保留。加载和保存 schema v7 时，校验器对保护范围采用“审计模式”：检查分钟记录自身合法性并生成 `minute-reconciliation` 差异，但不要求它聚合等于受保护 5 分钟。保护范围之外仍使用现有严格 1 分钟到 5 分钟校验。策略层继续使用 1 分钟判断事件先后，不新增可见周期。

**替代方案：** 删除保护范围内的 1 分钟，使 5 分钟成为唯一事实。该方案会损失已经实现的精确入场/出场判断，因此不采用。

### 4. 复用现有具体合约匹配器，但禁用启发式猜测

主连修复按交易日生成与现有 `DesktopMainMatchMinuteRecord` 等价的标准记录，并复用现有逐分钟候选比较、相邻交易日源差异和换月边界源差异审计结构。候选具体合约按以下优先级取得：

1. 优先使用同花顺同一 K 线接口取得的玻璃具体合约 5 分钟序列，并保留提供方原始代码；
2. 同花顺具体合约不可取得时，可使用项目已有、来源可审计的玻璃具体合约分钟序列作为候选，但必须经过现有跨源受限差异规则；
3. 两类来源均无法产生唯一证据时，该交易日保持未解决并阻止激活。

保护区间允许的方法只有：

- `exact-minute-sequence`；
- `neighbor-confirmed-source-variance`；
- `rollover-boundary-source-variance`。

`heuristic-fallback` 在本修复流程中禁用。价格跳变只能出现在报告中，不能作为候选选择条件。郑商所三位年份代码在领域层规范为四位年份代码，报告同时保留原始代码和规范代码。最终换月记录从完整映射重新生成，并校验 `FG2309 -> FG2401` 等变化只发生在被证明的新合约生效交易日。

**替代方案：** 直接采用当前 EDB 日映射或按价格跳变移动换月日。当前问题正是不同来源换月选择不一致，因此这两种方案都不能证明同花顺主连实际使用的合约。

### 5. 引入 schema v7 表达存储形态和基准保护

schema v7 使用判别式 `storage`，避免继续依赖“版本号同时代表完整快照或尾部层”的隐含语义：

```text
schemaVersion: 7
storage:
  kind: full
或
storage:
  kind: tail
  base:
    snapshotId
    metadataSha256
  replacementCutoff
  layerSequence
benchmarkProtection:
  provider: THS
  sourceSegmentId
  bars5:
    firstStart
    lastEnd
    protectedFields: [open, high, low, close, volume]
  bars60:
    firstStart
    lastEnd
    derivedFrom: bars5
  mappings:
    firstTradingDate
    lastTradingDate
  rollovers:
    firstTradingDate
    lastTradingDate
  minutePolicy: preserved-audit-only
  reportSha256
```

`MarketSnapshotSourceKind` 增加 `benchmark-main`，同花顺来源分段声明 `redistributionAllowed: false`，后续 EDB 尾部继续使用 `edb-tail`。首次修复写完整 v7 快照；在线更新可以继续写 v7 尾部层。尾部层可包含为聚合所需的重叠记录，但保存前必须逐字段证明所有保护内容与基准基座相同。

加载器继续支持 v1-v6，并对 v7 执行额外保护校验。v6 及更旧应用会拒绝 v7 元数据，然后通过既有 activated 快照扫描回退。清理策略除当前 v7 链外，还保留最后一份可由 v6 读取的激活快照作为兼容锚点；新版加载器优先选择仍被有效基准保护记录引用的 v7 链，避免未理解保护语义的旧版写入被误当成基准升级。

**替代方案：** 在 v6 上增加可选字段。旧版会忽略未知字段并把快照当作普通尾部层处理，存在覆盖校准历史的风险，因此必须升级 schema。

### 6. 在更新协调器中集中执行保护合并

新增纯领域函数负责按 `benchmarkProtection` 合并当前快照和 EDB 更新候选，避免把边界判断散落在在线状态机、保存器和 GUI 中。更新流程仍可从较早时间请求重叠数据以验证连续性，但合并行为改为：

1. 保留保护范围内的最终 5/60 分钟、映射和换月；
2. 合并或保存保护范围内的 1 分钟仅用于后台证据与差异报告；
3. 仅接受起始时间不早于 `bars5.lastEnd` 的新 1 分钟参与新 5 分钟聚合；
4. 从“受保护前缀 + 新 5 分钟尾部”计算新的 60 分钟数组；
5. 仅合并晚于 `mappings.lastTradingDate` 的新映射，再从完整映射生成换月；
6. 保存前比较保护指纹，任一变化均使候选失败。

完整补齐门禁保持现有顺序：加载最后有效快照、请求 EDB、合并并校验、原子激活、确认达到 `sourceLatestAt`、进入在线等待。这样仍满足“先更新到最新，再开始实时更新”。

**替代方案：** 让 `OnlineMarketCoordinator` 直接裁剪 EDB 返回。状态机不了解 K 线、交易日和快照来源语义，会导致手动更新与自动更新行为不一致，因此不采用。

### 7. 原子激活沿用现有 staging 机制并增加报告绑定

修复 CLI 构造完整 `SnapshotCandidate` 后调用扩展的快照保存器。保存器在 staging 目录写入数据和 v7 元数据，重新加载并执行全部校验，然后才重命名目录和切换当前指针。`benchmarkProtection.reportSha256` 指向运行目录中最终不可变报告的哈希，激活报告反向记录快照 ID 和 metadata 哈希。

指针切换前失败时删除 staging 快照但保留修复运行目录；指针切换后重新加载失败时按现有候选发现逻辑回退上一激活快照。快照清理不得删除当前 v7 尾部层引用的基座、最近兼容锚点或激活报告引用的保护快照。

### 8. 发布隔离通过来源声明和构建审计双重保证

同花顺修复目录位于 AppData，不在 `package.json` 的 `extraFiles` 来源树下。除此之外，发布校验和基线审计还要显式拒绝：

- `sourceSegments.kind === benchmark-main` 且 `redistributionAllowed !== true`；
- metadata 含 `benchmarkProtection.provider === THS` 的仓库内置资源；
- 同花顺原始响应、规范化 CSV 或修复报告出现在 `data/`、`build/`、`dist/` 或发布暂存目录。

仅依赖目录位置不足以防止人工复制，因此保留来源声明检查。

## Risks / Trade-offs

- [同花顺接口结构或分页行为变化] → 对响应做严格结构校验，保存原始页和请求参数；未知字段可忽略，必需字段变化立即终止且不影响当前快照。
- [同花顺具体合约数据不可取得] → 允许使用可审计的已有具体合约源走受限差异匹配；仍不能唯一证明的交易日阻止激活，不退回价格跳变猜测。
- [保留的 EDB 1 分钟与同花顺 5 分钟不一致] → 在保护区间采用审计模式并明确权威矩阵；1 分钟继续用于事件先后，但不能反向改写可见周期。
- [v7 增加加载和清理复杂度] → 使用判别式 `storage`、集中解析与保护指纹校验，并补充完整链、损坏链、旧版回退和压缩测试。
- [本地完整快照占用空间] → 首次修复必须写完整快照以建立清晰基座，后续分钟更新继续使用有界尾部层和既有压缩阈值。
- [旧版本回退后看到修复前数据] → 保留兼容锚点只用于安全降级；新版重新启动时优先恢复有效 v7 基准链，不把旧版无保护写入自动提升为基准。
- [授权不明确导致无法分发修复结果] → 功能按本机 AppData 交付，发布审计默认拒绝；授权结论变化应另建变更评估内置基线。

## Migration Plan

1. 先实现同花顺客户端、规范化器、差异报告和具体合约匹配适配，使用 fixture 完成离线测试，不改变任何有效快照。
2. 增加 schema v7 读写、保护校验、兼容锚点和更新合并测试；确认 v1-v6 继续可读，未知或损坏 v7 会回退。
3. 以只比较模式对当前 `glass_main` 运行，核对 83,088 根时间戳、示例换月日、OHLCV 差异和持仓保留报告。
4. 使用 `--activate` 生成并原子激活本机 v7 完整快照，重新加载后验证 5/60 分钟、映射、换月、离线复盘和双周期定位。
5. 开启在线模式执行一次完整 EDB 补齐，确认只在保护边界之后接续，再验证后续每分钟收盘更新。
6. 运行发布资源审计，确认 Git 工作树、`data/`、EXE 和安装包不包含同花顺数据。

回滚时将当前指针恢复到修复前最后有效兼容快照，或删除无效 v7 当前指针后由候选发现机制自动回退。修复运行目录和失败报告保留用于诊断，不参与运行时加载。
